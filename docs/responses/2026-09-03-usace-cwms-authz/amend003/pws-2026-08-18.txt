1.2 Background
The mission of the IWR HEC is to serve as the USACE Center of Expertise in the technical areas of surface and groundwater hydrology, river hydraulics and sediment  transport, hydrologic statistics and risk analysis, reservoir system analysis, planning analysis, real-time water control management and a number of other closely associated technical subjects. HEC's primary goal is to support the nation in its water resources management responsibilities by increasing USACE’s technical capability in hydrologic engineering and water resources planning and management. In addition to supporting USACE along with Division and District Offices, HEC provides technical support to the Corps overseas. Additionally, HEC provides services to other Federal, state, local and international agencies engaged in these technical areas.
The primary way HEC accomplishes this mission is by developing state-of-the-art software tools bringing them to state-of-the practice that are reliably used by water resources engineers and planners. Since its inception in 1964, HEC has been developing and integrating software tools that support the water resources computing requirements for Corps field offices, headquarters, laboratories, and other Federal, state, and international agencies. 
The CWMS is the Army Information System (AIS) that supports and enhances the decision-making process for the USACE water management mission. USACE is responsible for round-the-clock monitoring and operation of approximately 600 reservoir, lock and dam, and other water control projects. This responsibility also expands, during flood control operations, to approximately 120 additional Section 7 (Non-USACE) projects. Section 7 dams are non-USACE-owned dams for which the USACE prescribes regulations for flood control or navigation operations. These projects are operated under the authority of Section 7 of the Flood Control Act of 1944, which dictates how the Corps manages storage for flood risk management, while the dam owner manages the remaining storage.
CWMS provides critical information for making decisions that are fundamental in achieving the full range of benefits of the authorized purposes of USACE projects. CWMS integrates real-time data acquisition, database storage, flow forecasting of watershed runoff, reservoir operation decision support, river profile computation, inundated area determination, consequence analysis, and information dissemination into a comprehensive software package. CWMS and associated software underpin the USACE Water Management Enterprise System (WMES) by acquiring, processing, and reporting the hydrometeorological data required to manage USACE water resources projects under routine and emergency conditions. CWMS incorporates state-of-the-art modeling techniques such as spatially distributed rainfall-runoff flow forecasting, rule-based reservoir systems operation, steady and unsteady-flow water surface profile analysis, 2-D flow analysis, event-by-event flow impact for damage and life-loss estimation. In addition to determining reservoir operations, current and forecasted river water surface elevation/profiles and inundated flood area information can be utilized for flood fight decisions, flood evacuation warnings, and transportation interruption alerts. 
The focus of this contract is on the database and API components of our CWMS system.  CWMS is currently going through a transition from maintaining 32 independent, and geographically isolated systems, that feed into a public only central database, to a "single" cloud based system that will contain all data, both public and private. Part of this transition is merging the multiple District databases into an Oracle RDS instance with an HTTP REST API called CWMS-Data-API (CDA). Previous to this decision, much of the data authorization was done within each individual database so that appropriate data constraints could be implemented while allowing District applications to access Oracle directly. The CWMS Database Schema (CWMS DB) has thus made heavy use of session contexts and the Oracle Virtual Private Database (VPD) system to provide appropriate authorization. It is clear to us that this will not be sufficient going forward, and a more appropriate model of authorization needs to be adopted. While CWMS DB is currently using Oracle, is it likely the CWMS DB will migrate the data to various forms of storage appropriate to the type of data and its usage. As such, HEC believes it is most appropriate to focus our updated access control efforts on CDA, the API through which data will be accessed. CDA is a Java-based REST API using "javalin.io" as the underlying platform. The current Javelin AccessManager has changed from its initial implementation over time and will adapt to future requirements as needed.

Source Code Updates and Automated Tests
Updates to source code and build scripts must also include necessary updates to existing automated testing processes to proceed successfully. For example, new arguments in a function call might require updates to a related unit test, or a change in dependencies could require updates to a Docker container. This requirement applies to existing tests that require only minor updates for compatibility with the new improvements. Automated integration tests are required for authentication and authorization code. There is a central build system that runs the integration tests and the CWMS-Data-API and CWMS Database integration tests are structured in such a way to allow local running in one of three ways:
Using Docker, through the testcontainers-java library, the ready-database (as described in Technical Resources) is started, and the tests are run.
Using Docker, through the testcontainers-java library, a new database is created, the schema installed, and tests run. The schema will be reinstalled for each run.
The tests can be pointed at an existing Oracle database for faster cycling. NOTE: The tests assume they can do anything they want to that database; this method should not be used against a shared database.
Data should be loaded as appropriate at the start of the test. It is expected that new tools and helpers will be required as additional endpoints for data are constructed. The Contractor should follow the existing design patterns where appropriate; deviations should be coordinated and are appreciated when necessary. 
A specific, individual test for each element developed is not required. The goal of tests is to: 
Provide as-built style documentation 
Verify operation during refactoring and addition
Guide development so at least one initial usage is seen and used 
Prevent future regressions by documenting user issues that have been resolved
Tests should be designed in a way that shows natural usage of the API. The project goal is to have tests that cover all endpoints, not one test or test set per endpoint. If for any given set of controllers it appears better to create a test or set of tests that cover both at multiple data sources, then this is preferred.
The Junit5 platform and REST Assured are currently used for tests against the API.
At minimum, tests must exist to demonstrate that the access control implemented both succeeds and fails correctly. The preferred test locations, in order, are with the existing junit5 unit tests, the junit5 integration test suite, anything repeatable locally, and anything repeatable by the build server (currently TeamCity, actively being migrated to GitHub actions.)
The integration tests use the testcontainers-java library to create, or use, an instance of a CWMS Oracle Database. An extension was created that the tests use. If additional services are required for implementation of the access control methods, then the starting of such services for the integrations should be added to the existing extension or a new extension as appropriate.

The Authorization UI must:
 Allow District Administrators to create roles and policies, assign roles to users, and assign policies to roles.  
Allow District Administrators to be assigned to roles.
District Administrators should be able to do the following through the web Authorization UI:
Users Tab
View All Users who have roles/permissions assigned to access data for their district.
Assign roles to users for a specific district.
Show new users that do not have assigned privileges yet.
User registration can happen at any time.
Those users will have an account in the system, without any assigned roles.
User admins need to see a list of these users so that appropriate roles can be assigned.
Organize users by the assigned roles.
Would not be able to assign roles associated with data for districts that they do not have permission.
Roles Tab
Allow district administrators to create roles specific to that district’s data.
Allow administrators to assign policies to roles.
Be able to sort/filter roles by assigned policies.
Be able to view/edit/filter all roles associated with specific district’s data.
Administrators would not be able to edit roles for a district that they do not have permission to edit. 
Policy Tab
View policies associated with districts data.
Assign a time series to a policy.
Continue to use time series groups for this (or manage within the Authorization system) and allow districts to manage the time series in the Authorization UI.  Either restrictive or allowed. 
Assign based on time series parameters (LOC/parameter/version).
Assign embargo to time series.
Create policy and perform at least basic validation.

Technical Exhibit 3 Load testing
Given existing issues, and the addition of the new authorization steps, additional mass testing should be performed. Utilizing tools, such as but not limited to Apache JMeter, to do distributed load testing of data inserts, retrievals, updates, calculations (the rate endpoint) with a combination of authenticated and not-authenticated accounts against at least one single instance of CDA and one round-robin (at least two instances) instance of CDA. An Apache CloudStack environment can be provided to run these tests; however, more generic alternatives can be proposed. However, it is required that any developer can run these tests locally even if doing so would not reflect system performance – e.g. on a local development machine.
It should be reasonably easy for a developer to target a specific system to load test. 
The minimum facilities to be load tested are:
Authorization mechanisms
Time Series storage and retrieval, including catalogs of information
Location storage and retrieval, including catalogs of information
While testing of other components is desired, currently the focus is on setting up infrastructure to do any load testing. For this test, a single POST and GET of the requirement mechanism will be accepted. However, the analysis would benefit from using several different length time windows.
This testing is to establish baseline performance, as such there are no performance targets.
Desired test loads are as follows, or some combination thereof:
Single user, 50 request/second, parallelism of 10
100 users, 50 requests/second, parallelism of 10 (each)
1000 users, 100 requests/second
10000 request/second
100000 requests/second
For each scenario above, perform 1 instance of CDA, 2 instances of CDA (round-robin), and 3 instances of CDA (also round-robin) tests. Also, some combination of reads and writes, the vendor may assume the system is read heavy for this task.
Intent of data is to determine both RDS database vertical scaling or read replica requirements and if horizontal scaling benefits CDA usage.
Assume the CPU/memory specification to assume for CDA is 1 VCPU, 2GB RAM. 
As stated above, the goal is a baseline to analyze. The vendor is not expected to experiment with different scales or CPU/memory specs.

Technical Exhibit 4 Maintenance
The vendor will need to coordinate testing and bug reports with the community and correct discovered problems that are outside the scope of work performed for Technical Exhibit 1.
Provide maintenance to Authorization tools as real world testing is conducted, and it is applied to the needs of USACE staff.  Make improvements and adjustments based on user feedback and fix bugs that are found. The following list describes the type of activities to be performed as part of maintenance.   
Issue Classification. If the issue is a bug, then the contractor will identify the bug category, minor, routine, and major. The contractor will report status, via GitHub issue and receive direction to continue work after spending one hour classifying the issue. The contractor will also define the estimated amount of time to complete bug fixes and minor modifications or enhancements as part of issue classification.  
Bug Fixes in software code.  The contractor will report status, via GitHub Issue, and receive direction to continue work after spending two hours working on a bug fix. The contractor is directed to push draft code changes in a pull request after four hours of work have been completed, and document in the appropriate GitHub Issue.  
Minor Modifications and Enhancements. The contractor is directed to spend up to four hours, or as directed by HEC staff, completing a minor modification before reporting status, via GitHub Issue, and receiving direction to continue the work. The contractor is directed to push draft code changes in a pull request after four hours of work have been completed, and document in the appropriate GitHub Issue.  
Documentation. Software documentation is associated with the work completed above. 
Issue classification requires the evaluation of an issue to determine if the issue is:
a bug in existing code;
improper usage of the application or library;
a functionality gap in what the existing code is capable of doing and what the code needs to do.
Bug fixes are required for issues preventing appropriate usage of the software and be categorized as:
Minor Bug Fixes are those that normally require a few additional lines of logic/coding to be added to the existing code base. 
Routine Bug Fixes are those that normally require additional logic/coding, but require the addition of additional functions, procedures, objects to accomplish. 
Major Bug Fixes are those that require many hours of investigation to figure out the problem, and then many additional hours to modify the code in order to fix the problem. 
Functionality gaps in code are periodically identified. The work associated with a minor modification will normally require but is not limited to the following:
the creation of new script, function or procedure calls;
new classes or packages;
new tables or other database objects;
java code objects;
the creation of a new user function;
refactoring;
development of work-around methods or script approaches to accomplish special needs.
Documentation of work is any formal recording of what was done, how to use a software application, and reasoning behind design choices that developers and users can use to understand the workings of the system. Jira issue comments, while important, do not constitute documentation. Documentation may be provided by combination of any means appropriate to the given change, such as, but not limited to:
A manual test case that anyone can perform;
Javadocs;
Automated test case;
Formal project documentation.
